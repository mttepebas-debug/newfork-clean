- Excluded from Schedule (`employee_profiles.is_excluded_from_schedule`): the availability assessment already calls the person "Employee is not active in Schedule" (`weekly_assignment_candidate_base`). So a new shift by hand (`mutate_schedule_edit_shift_service` via `tests.add_shift`) and a pending op already fail 23514. The same check makes `publish_schedule_draft_service` hard-block ("schedule has hard publication blockers", preview code `schedule_conflict`) a week whose carried shift belongs to an excluded person, and `apply_schedule_template_service` refuses the whole apply ("Resolve availability ... before this assignment") instead of leaving that shift open. Tests: `excluded_person_leaves_new_drafts.test.sql`.
- Nobody can delete a location the owner works at today ("This location has employees you cannot manage"): BL-187, FB-6.2 .6. Cells that need it are `todo`.
- Before BL-218 `save_employee` ended every assignment and re-inserted them on each save (and crashed 23502 with no primary job). Since BL-218 it writes only the difference, so row-level rules on the assignment tables (owner stays at every live location, Owner job only on the owner, Management job never `is_primary`) see real removals only. A new rule of that kind must not assume end-all-reinsert.
- `update_job_assignments_service` makes a new assignment primary when the person has none; `open_owner_record_to_everything` never sets primary.
- Edit sessions: source `blank` = new draft (empty), `published` copies current published shifts (id = `source_shift_id`), `draft` copies a saved draft. Saving two sessions of one week with the same name fails "draft name conflict".
- Read a column that does not exist yet through `to_jsonb(row) ->> 'col'` so a red pgTAP file fails cell by cell instead of erroring out.

Related: [[rollback-trial-runner]].
- A redefinition copied from `pg_get_functiondef` must be checked against the live body right before commit: `artifacts/nf-db/bl218/difflive.sh` diffs each redefined function (live vs migration) so only the task's hunks show (BL-197/BL-188 bodies were at risk).
- Local reds that are not yours (measured 2026-09-27 18:37, no migration): schedule_edit_sessions 6, schedule_publication 2, schedule_requests 2, schedule_templates_autofill_export 1, shift_exchanges_v1 5, time_off_published_assignment_disposition ERROR. Compare counts with and without your migration before blaming it.
- `delete_catalog_entity_service` has no 'jobs' kind; jobs are deleted only by `delete_job_with_assignments_service`.
- The last migration file that names a function is not always its live body: some were patched in place later (e.g. `snapshot_document_lifecycle_requirement` gained acknowledgement handling in 20260916011654 without a `create function` line a grep finds). Take the base from `pg_get_functiondef` on the shared DB, not from the file (BL-252, 2026-09-28).
- Owner and documents (BL-246/252): an owner's documents are excused by `app_private.owner_document_excused` and marked `owner_excused`; any exemption is given or taken back through `app_private.set_document_exemption` (the reviewer's service, a transfer and a republish all call it). Taking one back re-derives `required`/`blocks_activation` via `app_private.document_requirement_asked`. Test world: `suspend_on_overdue` needs a `period_days`.
- In this Git Bash, `python3` is the Store stub and hangs; edit files with the Edit/Write tools or sed.
- Since BL-218.3b `save_employee` asks a non-owner record (not Remote, not excluded) for a location + primary location + a job, and for a primary job only when a job sits outside Management; hints `employee.location_required`, `employee.job_required`, `employee.primary_job_required` (22023). A non-owner with only a Management job saves with no primary. `tests.person` always passes `jobs[1]` as primary, so a Management-only person is built with `update_job_assignments_service` (give Manager, take the other job away).
- Since BL-218.3a the Schedule read (`get_schedule_read_model_service`) and the team board (`get_employee_schedule_board_service`, same `scheduleReadModelSchema`) return `primary_job_id` = the stored `is_primary` job or null, and `system_key` on departments and jobs. When a returned field's rule changes, grep `pg_proc.prosrc` for every function returning that field (the board was a missed twin, nf-guvenlik 2026-09-28). The web falls back itself in `scheduleEmployeeSort.ts` `primaryScheduleJobId(employee, jobs, departments)`, which since 84d5357f (BL-218.3, nf-backend) also gives a new shift's default job in `shiftEditorState.ts`. A rule that decides by catalog membership (Management, Owner) is bound to the target workspace, or the refusal leaks what another workspace's uuid is (nf-guvenlik, 2026-09-28).
- Two reads that answer in one schema (the Schedule read and the employee team board, both `scheduleReadModelSchema`) take their shared parts from one `app_private` helper (`schedule_departments_and_jobs`, `stored_primary_job`, BL-218.3), and a structural pgTAP cell keeps them there (`reads_know_management_and_owner`: both bodies call the helpers and contain no `is_primary`). A display fallback computed in SQL (Employees list `primary_job_name`: stored primary, else first Management job, else first job) follows the web's `primaryScheduleJobId` order, so the list and Schedule name the same job.
- Since EMP-001 (2026-09-30) "manages without working there" is gone: `actor().manages` = `works` for a manager. K4: every manager who is not Remote keeps a location, excluded or not (`app_private.keep_manager_at_a_location`, 22023 hint `employee.manager_location_required`), on save, "Remove from <location>", role change to manager and an invitation as manager. A test that takes a one-location manager off their location now gets 22023: use one with two (matrix target `pl:can@K`). `tests.person` with no locations builds a Remote person, who is exempt. For anybody neither Remote nor excluded the older rules answer first on save (`employee.location_required`) and would on an invitation ("employee requires a location before invitation", no hint).
- An entry point moved onto the core also gets `authz.workspace_closed`: a draft workspace (setup not finished) is open to its owner only (`app_private.workspace_open_to_actor`). A hand-built fixture that inserts staff into a workspace from `create_owner_workspace_service` must finish setup first: a location, a department and job, then `update_owner_onboarding_service(owner, w, name, 4::smallint, true, revision, first, middle, last)` with the owner legal name (`own_employment_record.test.sql`).

A `member` action on a person target needs the "not on somebody else" line before the `restricted_ok` line in `expected()` (there since BL-443). An onboarding persona (aydan) has no private profile until `save_employee_onboarding_profile_service` is called for her.
