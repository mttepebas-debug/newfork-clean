### 2026-07-28T07:23:09.496Z

Root cause: the `pay_entities` RLS SELECT policy is `app.backend_context() AND organization_id = app.current_org_id() AND app.member_has_org_permission('settings_labor.read')`. `member_has_org_permission` only passes when `role_permissions.scope_type = 'org'`, and the built-in `manager` role holds `settings_labor.read` at `location` scope. So `pay_entities` rows are invisible to every manager.

Any Prisma query that selects the REQUIRED `pay_entity` relation (schema.prisma: `pay_entity PayEntity @relation(...)`, non-optional) therefore throws:
  PrismaClientUnknownRequestError: Inconsistent query result: Field pay_entity is required to return data, got `null` instead
which surfaces as a 500.

Already fixed (2026-07-28, commit on main): `apps/api/src/features/locations/locations.service.ts` `listLocations` — GET /locations 500'd for every manager in an organization that has at least one location. It now selects `pay_entity_id` and resolves the display name with a separate `tx.payEntity.findMany`, yielding `pay_entity_name: null` when RLS hides the row.

Still unfixed, same pattern, all on manager-reachable surfaces (see the role-access allowlist in apps/api/src/role-access.integration.test.ts):
- apps/api/src/features/employees/employees.service.ts:1257 — employee detail (`GET /employees/:id`). Proven to 500 for an org-scoped manager.
- apps/api/src/features/employment-events/employment-events.service.ts:203 — `GET /employees/:id/employment-events`.
- apps/api/src/features/employment-events/new-hire-reporting-queue.service.ts:63 — `GET /new-hire-reporting-queue`.
- apps/api/src/features/locations/locations.route.ts:161 — location compliance read; check whether it is manager-reachable.

Two candidate fixes — pick deliberately, do not do both:
(a) Repeat the locations.service.ts pattern at each site (no migration, no access change, names come back null for managers).
(b) One migration widening `pay_entities_select` so a member with `settings_labor.read` at ANY scope can read the pay entities of locations they can see. This fixes every site at once but is a real access-control decision on a payroll-adjacent table and needs the founder's sign-off. Migrations are serialized — check `git status supabase/migrations` first.

Verify behaviourally, not by reading policies: build a manager with a `member_scopes` row and drive the routes through `buildApp()` + `app.inject()`. `apps/api/src/location-scoping.integration.test.ts` already has that fixture and can be extended.
