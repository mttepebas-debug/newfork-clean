Build a behavioural integration test proving location scoping inside a single organization: a manager scoped to location A must not be able to read or mutate location B's data, even though both locations belong to the same org.
Why this is the remaining gap
Two sweeps already landed on main and cover the neighbouring axes. Read them first — they are the templates for this work:

* `apps/api/src/rls-cross-tenant.integration.test.ts` — org-vs-org isolation. Seeds two orgs via the real `signupOwner` + `createShift` services, then for every table holding org A rows, reads it back under org B's tenant context and requires zero visible rows.
* `apps/api/src/role-access.integration.test.ts` — role isolation. Signs in a real `employee`-role member (Supabase user + active membership + live access token) and drives all 577 registered routes with `Authorization: Bearer <token>` + `X-Organization-Id`, asserting set equality against a frozen allowlist of the 39 routes an employee may be served.

Neither proves location scoping. Both test users are org-wide. The uncovered question: can a manager scoped to location A see location B's shifts, employees, schedules and time entries? This is a core product rule in CLAUDE.md ("Location scoping", "Never expose data from one organization or location to unauthorized users") and it is currently unproven by any automated test.
Scope
Same org. Two locations. A manager whose `member_scopes` row grants location A only.
Assert that location B's data is invisible/unreachable through the real service and route layers — not just that a policy mentions `location_id`. Cover at minimum: shifts, employees, schedules/drafts, and time entries. Extend if the seeding makes other surfaces cheap.
Watch for the scope mechanism: membership scoping lives in `member_scopes` (`scope_type` = `'org'` | `'location'`, `scope_id`). `signupOwner` creates an org-scoped owner. Look at `apps/api/src/features/roles/roles.integration.test.ts` (`memberActorWithRole`, `memberActorWithCustomRole`) for how members and roles are created, and at `app.requirePermission` / `locationAccessForPermission` in `apps/api/src/plugins/permissions.ts` for how location access is resolved per permission grant.
Prefer driving real HTTP through `buildApp()` + `app.inject()` (as role-access does) over calling services directly, so route guards are exercised too. A grant-level catalog check is not enough — this must be behavioural.
