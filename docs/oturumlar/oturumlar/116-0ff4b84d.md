### 2026-08-04T06:22:16.807Z

GET /pay-entities/default/readiness returns 409 `default_pay_entity_missing` ("This organization has no default pay entity.") when the caller CAN see the route but the pay entity row is invisible under their RLS scope.

Reproduced 2026-08-04 against a local Supabase stack via apps/api/src/role-access.integration.test.ts: an admin gets 200 with a real entity, a manager on the same org gets 409 saying the org has none.

Cause: `resolveDefaultPayEntityReadiness` in apps/api/src/features/pay-entities/pay-entity-readiness.service.ts does `tx.payEntity.findFirst(...)` under `withTenantContext` and throws `DefaultPayEntityMissingError` when it finds nothing. The `pay_entities_select` RLS policy serves a location-scoped `settings_labor.read` holder only the entities their assigned locations belong to (admin/owner hold the key at org scope, manager at location scope — see migration 20260802110000). A manager with no member_scopes, or scoped only to locations not assigned to that entity, reads zero rows and is told the organization has none.

Impact: the message is wrong and actively misdirects — it tells a manager to create a pay entity they have no permission to create. Narrow in practice (the MVP has one pay entity and locations are assigned to it), but it is exactly the "confusing permission behaviour" CLAUDE.md calls out.

Decide and implement one of: (a) distinguish "no default pay entity exists" from "not visible in your scope" and word each for its audience, or (b) return the readiness payload with an explicit not-visible marker so the payroll hand-off page can render a real explanation. Note that (a) needs a scope-free existence check to tell the two apart.

Do not regress apps/api/src/role-access.integration.test.ts, which now lists this route under ADMIN_ADDS with the reasoning recorded, or pay-entity-readiness.route.test.ts, which pins the settings_labor.review split that withholds the org-wide worksite list.

## Asistanın son mesajı

Chose (a) — distinguish, without the scope-free existence check.

**Why not a scope-free check.** It would need `withServiceRole` (ratcheted surface, doc entry) or a new SECURITY DEFINER function (migration). Not needed: an empty read is *inconclusive* only for a location-scoped reader. So ask the same helper the policy asks —

```ts
SELECT app.member_has_org_permission('settings_labor.read') AS allowed
```

`allowed` → the read was org-wide, absence is real → `default_pay_entity_missing` keeps its wording. Not allowed → `default_pay_entity_not_visible`, 409, "You are not assigned to a location on this organization's pay entity… Ask an administrator for access." Precedent for this exact raw call already exists in `time-entries.service.ts:7376`. Only runs when the entity read is empty.

**Second door, same root cause.** `assertDefaultPayEntityReady` runs the same resolver before payroll-handoff create + ready, and `payroll-handoff.route.ts` mapped *neither* absent-entity error — a scoped-out manager got a bare 500 there. Both map now.

Web needs no change: `PayrollHandoffPanel` renders `errorMessage(setupQ.error, …)`, which surfaces the server `message`.
